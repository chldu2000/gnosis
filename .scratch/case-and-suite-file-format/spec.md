# 用例与套件的文件格式与载入

## Problem Statement

测试编写者要把一条测试写成文件，交给 Gnosis 执行。现在没有这样的文件格式。没有它，桌面端没法保存用例，命令行没法执行用例，套件也没法把用例串起来。

编写者还需要知道文件哪里写错了。写错的用例不能被悄悄执行成另一个样子，也不能被悄悄改写。

## Solution

定义两种文本文件：**用例**文件和**套件**文件，并提供一个**载入**入口。

- 用例文件是一条用例：有名称，有序的步骤。步骤只有三种：动作、断言、AI 步骤。
- 套件文件是有序的一组用例引用，路径相对于套件文件本身。
- 载入一个用例文件，得到一条可以直接执行的用例；载入一个套件文件，得到一个套件，其中每条被引用的用例都已读到并检查过。
- 文件里有任何读不出来的地方，载入就拒绝，并说出是哪个文件的哪一处。载入从不修改任何文件。

## User Stories

1. 作为测试编写者，我想把一条测试写成一个用例文件，这样可以用普通文本编辑器和版本管理来维护它。
2. 作为测试编写者，我想给用例起一个名称，这样报告里能认出这是哪条用例。
3. 作为测试编写者，我想在没写名称时由文件名充当用例名称，这样小用例不用重复写一遍。
4. 作为测试编写者，我想让两条用例使用同一个名称，这样不同目录里的同类用例不会被强制改名。
5. 作为测试编写者，我想用有序的步骤描述用例，这样执行顺序和我写的顺序一致。
6. 作为测试编写者，我想给某个步骤起名称，这样报告里能直接看到这一步在做什么。
7. 作为测试编写者，我想不给步骤起名称，这样简单的步骤写起来不啰嗦。
8. 作为测试编写者，我想写出启动应用这一步，并给出应用标识，这样用例可以从应用启动开始。
9. 作为测试编写者，我想在启动应用时省略入口，这样用应用自己的入口就够了。
10. 作为测试编写者，我想在启动应用时写出入口，这样可以直接打开某个 Activity 或 Ability。
11. 作为测试编写者，我想写点击这一步，并给出定位器，这样可以点中一个指定的元素。
12. 作为测试编写者，我想写长按这一步，并给出定位器，这样可以长按一个元素。
13. 作为测试编写者，我想长按没写时长时按 800 毫秒，这样常见情况不用重复写。
14. 作为测试编写者，我想在长按上自己写出时长，这样需要更久时可以改。
15. 作为测试编写者，我想写按比例点击这一步，用屏幕宽高的比例给出位置，这样树和 OCR 都找不到时仍能点一个位置。
16. 作为测试编写者，我想写滑动这一步，用屏幕宽高的比例给出起点和终点，这样换分辨率不用改用例。
17. 作为测试编写者，我想滑动没写时长时按 300 毫秒，这样常见情况不用重复写。
18. 作为测试编写者，我想在滑动上自己写出时长，这样需要更慢或更快时可以改。
19. 作为测试编写者，我想写输入文本这一步，给出要输入的文字，这样可以往当前焦点里输入。
20. 作为测试编写者，我想写按键这一步，选择返回或主页，这样可以离开当前界面。
21. 作为测试编写者，我想写等待这一步，必须给出时长，这样不会忘记自己等了多久。
22. 作为测试编写者，我想在等待没有写时长时被拒绝，这样不会得到一个隐含的默认时长。
23. 作为测试编写者，我想用同一种写法描述定位器，这样 Android 和 HarmonyOS NEXT 的用例互相能看懂。
24. 作为测试编写者，我想在定位器里用资源 id、显示文本、描述、类型和第 n 个作为条件，这样可以区分两个都叫「确定」的按钮。
25. 作为测试编写者，我想定位器里的第 n 个从 1 开始，这样 1 就是第一个匹配。
26. 作为测试编写者，我想写出前置断言，这样前提不满足时用例阻塞，而不是失败。
27. 作为测试编写者，我想写出预期断言，这样用例有没有达到目标可以被判定。
28. 作为测试编写者，我想每条断言明确写出它是前置还是预期，这样不会因为位置而搞混。
29. 作为测试编写者，我想把前置断言放在序列的任意位置，包括开头，这样既能保护整个用例，也能保护后面某一步。
30. 作为测试编写者，我想写元素存在和元素不存在这两种断言，这样可以检查某个元素有没有出现。
31. 作为测试编写者，我想写文本等于和文本包含这两种断言，这样可以检查显示文本。
32. 作为测试编写者，我想写属性等于这种断言，并限定为可用或选中，这样两个平台都能用。
33. 作为测试编写者，我想写屏幕上看得见某段文字这种断言，这样自绘的界面也能检查。
34. 作为测试编写者，我想断言没写时限时按 10 秒，这样常见情况不用重复写。
35. 作为测试编写者，我想在每条断言上自己写时限，这样慢的界面可以等久一点。
36. 作为测试编写者，我想写 AI 步骤，给出一段目标，这样可以用自然语言描述要在设备上达成什么。
37. 作为测试编写者，我想 AI 步骤没写步数上限时按 20 步，这样常见情况不用重复写。
38. 作为测试编写者，我想在 AI 步骤上自己写步数上限，这样复杂任务可以多给几步。
39. 作为测试编写者，我想把脚本步骤和 AI 步骤写在同一条用例里，这样两种流程可以混用。
40. 作为测试编写者，我想只有一个 AI 步骤的用例也是普通用例，这样单独跑一个 AI 任务不需要另一种文件。
41. 作为测试编写者，我想一个步骤都没有的用例也能载入，这样可以先建好空用例再慢慢写。
42. 作为测试编写者，我想用例里写错了字段名时被拒绝，并看到是哪个文件的哪一处，这样拼写错误不会被悄悄忽略。
43. 作为测试编写者，我想遇到第一版不认识的字段也被拒绝，这样新旧版本之间不会悄悄丢掉我写的内容。
44. 作为测试编写者，我想缺少必填内容时被拒绝并指出位置，这样不会得到一条残缺的用例。
45. 作为测试编写者，我想写错了类型时被拒绝并指出位置，这样把数字写成文字的错误当场就能发现。
46. 作为测试编写者，我想载入这个动作从不修改我的文件，这样出错时我的原稿还在。
47. 作为套件维护者，我想把一组用例写成套件文件，这样可以在同一台设备上依次执行它们。
48. 作为套件维护者，我想在套件里用相对于套件文件的路径引用用例，这样整个目录可以整体搬走。
49. 作为套件维护者，我想在套件里引用同一条用例两次，这样想跑两遍时不用复制文件。
50. 作为套件维护者，我想有一条被引用的用例读不到时，整个套件被拒绝，这样不会出现跑了一半才发现缺文件的情况。
51. 作为套件维护者，我想被引用的用例里有错时，整个套件被拒绝，并说出是套件里第几条引用、哪个用例文件、哪一处，这样可以直接去改。
52. 作为套件维护者，我想空的套件被拒绝，这样不会得到一个没有任何用例的执行。
53. 作为套件维护者，我想套件文件里有不认识的字段时也被拒绝，这样规则和用例文件一致。
54. 作为命令行使用者，我想载入失败时拿到可读的位置信息，这样可以在流水线日志里直接看到哪里错了。
55. 作为命令行使用者，我想载入结果不依赖任何设备或网络，这样可以在没有设备的机器上先检查文件。
56. 作为桌面端的开发者，我想用同一个载入入口读用例和套件，这样桌面端和命令行看到的是同一份内容。
57. 作为桌面端的开发者，我想载入失败时有明确的文件和位置，这样表单里可以指出哪里要改。
58. 作为执行器的开发者，我想载入结果里已经带上所有默认值，这样执行器不需要再知道默认值是多少。
59. 作为执行器的开发者，我想载入结果保持步骤的原有顺序，这样报告里的序号和文件里的顺序一致。
60. 作为执行器的开发者，我想点击和滑动的比例即使不在 0 到 1 之内也原样保留，这样越界仍由执行时报告为错误，而不是被当成读不出来的文件。

## Implementation Decisions

- 文件是 YAML 文本，使用 UTF-8。一个用例一份文件，套件是另一份文件。
- 对外只有一个**载入**入口。入口接受一个文件路径，也能判断它是用例文件还是套件文件。
- 载入的结果是以下两种之一：
  - 一条用例：名称，以及有序的步骤。步骤带有它自己的名称、种类和已经补全的默认值。
  - 一个套件：有序的一组已经载入的用例；同一个用例文件被引用两次时，就是两份独立的用例。
- 载入失败的结果是一个拒绝，包含三部分：哪个文件、文件里的哪一处、为什么。套件里引用的用例出了问题时，还要带上这是套件里的第几条引用。
- 载入从不写文件，包括不重排、不补全、不改写。
- 步骤只有三种：
  - **动作**：启动应用（应用标识，可选入口）、点击（定位器）、长按（定位器，可选时长）、按比例点击（两个比例）、滑动（起点和终点的比例，可选时长）、输入文本（文字）、按键（返回或主页）、等待（必填时长）。
  - **断言**：标明是前置断言还是预期断言，再加一种陈述：元素存在、元素不存在、文本等于、文本包含、属性等于（属性只能是可用或选中）、屏幕上看得见某段文字。可选时限。
  - **AI 步骤**：一段目标，可选步数上限。
- 默认值由载入补全：断言时限 10 秒，长按 800 毫秒，滑动 300 毫秒，AI 步骤步数上限 20 步。等待没有默认值。
- 定位器的条件是资源 id、显示文本、描述、类型和第 n 个，第 n 个从 1 起。两个平台使用同一种写法。
- 用例名称没写时，取文件名去掉扩展名之后的部分。名称可以重复。
- 步骤的名称是可选的。载入结果保持步骤的原有顺序。
- 用例可以没有任何步骤，载入成功。套件不能为空，载入拒绝。
- 套件文件用相对于套件文件所在位置的路径引用用例。载入套件时，先读完所有引用，任何一条读不出来或没通过载入，整个套件被拒绝，不返回部分结果。
- 不认识的字段、不认识的步骤种类、缺少的必填内容、类型不对的值，一律拒绝。
- 比例只检查是不是数字，不检查是否在 0 到 1 之内。越界由执行时作为错误处理。
- 设备、模型地址、模型名、密钥都不属于用例或套件，文件里也没有地方可以写它们。

## Testing Decisions

- 好的测试只通过载入入口看外部行为：给一个文件，看得到什么结果，或被拒绝时说了哪一处。不测内部的字段解析函数。
- 只设一个接缝，即载入。每条测试用固定样例文件，放在测试专用目录，必要时在临时目录里拼出套件和它引用的用例。
- 要覆盖的行为：
  - 三种步骤的每一种写法载入正确，默认值已补全；
  - 名称缺省取文件名；名称重复可以载入；
  - 空用例载入成功；空套件被拒绝；
  - 不认识的字段、缺少的必填内容、错误的类型被拒绝，并指出文件和位置；
  - 等待缺少时长被拒绝；
  - 点击和滑动的比例越界时仍能载入，并保持原值；
  - 套件相对路径的解析，同一用例被引用两次；
  - 套件里某条引用读不到或有错时，整个套件被拒绝，并指出第几条引用和哪个用例文件；
  - 载入前后文件内容完全相同。
- 仓库里还没有任何测试，没有前例可循；使用 Go 的标准测试方式和表驱动写法。
- 载入不依赖设备、模型和网络，所以这些测试可以在任何机器上运行。

## Out of Scope

- 执行，包括设备连接、断言的轮询、AI 循环、OCR 和报告。
- 检查应用标识是否真的存在、元素是否真的存在。这些只有执行时才知道。
- 比例越界时产生错误，那是执行的事。
- 命令行的退出码和桌面端的表单。它们使用载入的结果，但不属于这份规格。
- 把轨迹导回用例，以及录制。
- 套件里的并行、重跑、条件和分支。

## Further Notes

访谈里没有定下来、这份规格先按建议处理的几处。动手前请确认或修改：

1. **文件里的字段名。** 访谈里只定了概念，没定 YAML 里具体叫什么。建议字段名用英文标识符，界面和报告里再显示中文术语。
2. **时长的写法。** 建议写成数字加单位，毫秒或秒，不允许省略单位。
3. **断言的位置没有默认。** 每条断言必须明确写前置或预期，不写就被拒绝。
4. **定位器至少要有一个条件。** 只写第 n 个也算一个条件还是不算，没有定过。建议第 n 个必须搭配至少一个其他条件。
5. **第 n 个小于 1。** 建议载入时拒绝。它和比例越界不同：比例越界按 Q45 是执行时的错误，所以载入保留；第 n 个小于 1 没有这样的约定。
6. **套件里的引用能不能是绝对路径。** 没定过，建议第一版也拒绝，只接受相对路径。
7. **套件有没有自己的名称。** 套件没有结果，报告也只针对执行。建议第一版套件不写名称。
8. **重复的 YAML 键。** 建议拒绝，不是取最后一个。
