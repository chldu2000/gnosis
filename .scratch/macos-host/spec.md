# Gnosis macOS 宿主支持

## Problem Statement

使用 Mac 的测试人员需要在自己的电脑上执行已有的用例和套件，并取得带截图的报告。现行首发设计只承诺 Windows 宿主。Android CLI 已在 Apple Silicon 上通过构建和现有自动化测试，Intel 版已交叉编译。Android 真机、屏幕文字识别和 Intel 实际执行仍需验证。现有桌面端依赖 Windows 的本机通信和凭据存储。

## Solution

现在开始 macOS 宿主适配，发布时间另定。第一批以 CLI 为验收入口，验证现有用例、套件、屏幕文字和报告。MyGo 桌面端另行验收。

## User Stories

以下故事定义首批 CLI 适配范围。

1. 作为使用 Mac 的测试人员，我希望知道支持的架构和最低 macOS 版本，以便确认发布物能在我的电脑上运行。
2. 作为已有用例的测试人员，我希望用同一份 YAML 在 Mac 上执行，以便在团队内共享用例。
3. 作为已有套件的测试人员，我希望相对引用和重复引用保留各自的执行位置，以便在不同宿主上得到一致的报告。
4. 作为连接多台设备的测试人员，我希望明确选定一台在线设备，以便把动作发给指定的设备。
5. 作为首次配置 Android 的测试人员，我希望能区分 ADB 服务未启动、设备未授权和设备离线，以便排查连接问题。
6. 作为共用设备的测试人员，我希望设备占用时收到拒绝原因，以便知道执行尚未开始。
7. 作为执行输入步骤的测试人员，我希望用例收尾时恢复设备原有输入法，以便继续正常使用设备。此场景安排在后续真机验收。
8. 作为需要判定屏幕文字的测试人员，我希望用内置资源离线识别中文，以便执行屏幕文字断言并使用定位器后备查找。
9. 作为遇到识别故障的测试人员，我希望区分 OCR 无法运行和屏幕文字不存在，以便理解用例的结果。
10. 作为在自动化中调用 CLI 的测试人员，我希望保留退出码、诊断和报告路径的行为，以便沿用现有调用方式。
11. 作为分享报告的测试人员，我希望复制一份报告及相邻附件后仍能离线浏览，以便把所见界面交给同事核对。
12. 作为使用符号链接或大小写不同路径的测试人员，我希望 Gnosis 能识别这些路径引用的目录，以便报告继续写在用例目录树外。
13. 作为复查历史执行的测试人员，我希望知道报告存放在哪里以及会保留多久，以便在之后找回记录。
14. 作为需要长期保存报告的测试人员，我希望在执行时指定报告目录，以便把报告保存在自己管理的位置。

## Implementation Decisions

### 已确认事项

- 适配现在开始，macOS 发布日期另定。
- 首批以 CLI 为验收入口。MyGo 桌面端放到后续阶段验收。
- 首批在 Apple Silicon Mac 上用 Android 真机验收。
- 沿用现有 ADB 流程。测试人员用 Platform-Tools 启动本机服务并授权设备，Gnosis 连接已启动的服务。CLI 使用说明应涵盖服务未启动、设备未授权和设备离线的排查方式。
- CLI 通过 `--report-dir` 指定本次执行的报告根目录，支持绝对路径和相对于当前工作目录的路径。省略参数时使用宿主的默认目录。CLI 在连接设备前校验报告位置，执行后打印报告的绝对路径，并将截图保存在同一个会话目录内。

### 现有约束

- macOS 是运行 Gnosis 的宿主。Android 和 HarmonyOS NEXT 仍是设备平台。用例、套件和步骤的格式沿用现行设计。
- Android 执行通过现有 ADB 协议与本机服务通信。设备端继续使用 uiautomator2。屏幕文字识别沿用离线 ONNX Runtime 和 PP-OCR，发布物需带与架构匹配的动态库和模型。OCR 不可用时沿用错误结果。参见 [设备协议决策](../../docs/adr/0002-device-protocol-not-cli.md) 和 [屏幕文字识别决策](../../docs/adr/0005-onnx-ppocr-in-core.md)。

本轮采用 ONNX Runtime 1.23.2 ARM64 动态库。CLI 的 Mach-O 部署下限为 macOS 13.0，动态库的部署下限为 13.4，因此有 OCR 的验收目标下限为 macOS 13.4。最低系统版本的运行验收仍需在该版本完成。正式分发方式和签名随发布范围确定。

## Testing Decisions

- 首批测试入口是公开 CLI。沿用现有 CLI 对退出码、报告路径和套件结果的测试，以及共享执行对设备占用、取消和报告的测试。新增覆盖针对 macOS 上出现的行为差异。在采用最低支持系统版本的 Apple Silicon Mac 上，用 CLI 连接 Android 真机，执行一份包含中文屏幕文字断言和重复用例引用的套件，并查阅离线报告。
- 通过公开 CLI 指定报告目录，验证绝对路径和相对路径都生成可读取的报告和截图，并在标准输出打印一次报告的绝对路径。
- 验收可见行为。用路径别名和符号链接核对报告仍在用例目录树外，用缺失或错误架构的动态库核对 OCR 错误，用正常的动态库完成真实推理。现有 Windows 构建与测试作为回归基线。

## Out of Scope

- 首批验收限 Apple Silicon 上的 Android CLI。Intel 与 HarmonyOS NEXT 单独安排实际执行验收。MyGo 桌面端、Finder 启动、Keychain 和应用包在后续阶段验收。云端调度、录制、测试资产格式扩展和新增设备操作由各自的规格定义。
- AdbKeyboard 安装、中文输入及输入法切换和恢复的真机验收，推后到有可安装 AdbKeyboard 的测试设备时进行。

## Further Notes

- 后续桌面端复用现有执行控制约定。Unix 域套接字、按需启动独立执行进程、Keychain 和应用包资源布局仍是候选方案。沿用 Windows 桌面验收场景，覆盖关窗后继续执行、同一设备仍被占用、重开恢复进度、取消和打开报告。确认 macOS 传输和资源布局后，补记它们与现有 ADR 的适用关系。参见 [独立执行进程决策](../../docs/adr/0006-keep-execution-outside-the-desktop-window.md) 和 [执行控制](../../docs/execution-control.md)。

### 2026-11-20 验收记录

- 在 macOS 27.0.1 ARM64 上，用 Go 1.27.4 和 `CGO_ENABLED=0` 原生构建 CLI。`--help` 显示 `--report-dir`。全量 Go 测试通过，覆盖绝对和相对报告目录、套件重复引用、截图附件、路径别名及符号链接。
- 使用 [ONNX Runtime 1.23.2 ARM64 wheel](https://pypi.org/project/onnxruntime/1.23.2/#files) 中的动态库、文档指定的 PP-OCRv5 模型和中文词典，通过 Android 适配器的 OCR 入口识别 640×224 的测试图。识别结果为「界面自动化」，返回的区域在图像边界内。缺少动态库和误放 Intel 动态库均得到 OCR 不可用错误。
- 在 macOS 上用两个进程争用同一占用锁，第二个进程在占用期间被拒绝，在释放后可以获得占用。
- Windows amd64 使用 `mygo_nowebview` 的全仓交叉构建和测试程序编译均通过。测试程序的执行需要 Windows 环境。
- 在 Android 16 真机上通过 USB 执行原生 CLI。能点击设置搜索框并保存截图。重复引用同一个屏幕文字用例时，两次结果均为 `pass`。复制会话目录后，Chromium 从相对路径载入截图，附件仍可解码。文字缺失得到 `fail`，缺失或错架构的动态库得到 `error`。另用真机截图和空控件树验证了定位器的屏幕文字后备查找。第二个 CLI 进程因设备占用退出并且未生成报告。
- 两次中文输入验收均在安装 AdbKeyboard 时被真机拒绝，错误为 `INSTALL_FAILED_USER_RESTRICTED`。报告如实记录首个用例为 `error` 和第二个用例未开始。输入法在两次尝试中都保持设备原有设置。这项真机验收已推后。首批仍需在 macOS 13.4 上验证部署下限。
