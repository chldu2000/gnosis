# Android 用例表达能力改进方向

本文档整理 Gnosis 在编写和执行 Android UI 自动化用例时遇到的表达能力缺口及改进方向。

优先级排序以**实际编写用例时最容易受阻的高频场景**为主，同时保持与 [`docs/design.md`](design.md) 和 [`GLOSSARY.md`](../GLOSSARY.md) 的一致：

- Android 与 HarmonyOS NEXT 共用同一套用例文件格式、定位器和设备操作语义；
- 用例保留为声明式的有序步骤序列，能由桌面端原生表单直接编辑和校验；
- 不把用例演进成通用脚本语言，柔性探索继续由 `ai` 步骤承担。

与当前设计定位存在明显冲突、或会破坏跨平台与桌面表单简洁性的能力，统一列在文末的**保留项**中，说明冲突原因、现有替代方式以及重新评估的前提条件。

---

## 一、高优先级：实际编写 Android 用例的高频卡点

### 1. 定位器的模糊匹配、层级限定与可见性过滤

#### 编写时的实际痛点

- **动态文本无法精确命中**：目前定位器（`Locator`）对 `id`、`text`、`description`、`type` 全部采用字面精确相等匹配。商品数量、倒计时、用户名拼接等动态显示文本（如 `"购物车(3)"`、`"立即购买 09:58"`）无法通过显示文本点击，只能退化成脆弱的 `tap_at` 比例点击或改用 `ai` 步骤。
- **扁平列表计数易错位**：`ControlTree()` 会将 Android 控件树节点拍平，丢弃父子与兄弟关系。在列表或卡片场景（例如“点击第 2 张商品卡片内的‘删除’按钮”）中，只要前面的卡片多或少一个辅助标签，全局扁平序号 `index` 就会错位。
- **屏幕外节点干扰定位**：控件树包含当前不在屏幕内的节点（例如 `RecyclerView` 预加载项或被弹窗遮挡的底层元素），定位器无法限定“仅匹配当前屏幕可见元素”，可能导致点偏或因为屏幕外有相同元素而触发多匹配错误。
- **屏幕文字后备条件过窄**：控件树零匹配后回退到屏幕文字识别时，只有定位器仅包含 `text`（及可选 `index`）且识别行文本**完全相等**时才能命中；遇到同一行有多个词或局部文字时容易失手。

#### 改进方向

1. **增加非精确文本匹配条件**：在定位器中补充子串匹配（如 `text_contains`、`description_contains`）或受限正则匹配，使动态显示文本无需退化到坐标点击。
2. **引入容器范围限定（相对定位）**：允许为定位器指定一个父容器定位器（例如 `within`），仅在该容器子树内过滤子元素并计算 `index`，避免列表结构微小变化导致全局序号偏移。
3. **支持可见性/屏幕内过滤**：在元素过滤阶段支持限定“位于当前屏幕可视范围内（且非零尺寸）”，减少列表预加载节点带来的误命中。
4. **放宽屏幕文字后备的匹配粒度**：评估在仅含显示文本的定位器后备查找中支持子串包含匹配（与 `screen_text` 断言保持一致）。

> **设计边界说明**：依据 [ADR-0003](adr/0003-tree-text-vs-pixel-text.md)，显示文本来自控件树、屏幕文字来自截图像素。上述扩展仍应坚持“先控件树、零匹配再屏幕文字”的查找顺序，不让像素识别覆盖控件树本身的能力边界。

---

### 2. 缺少“滚动直到元素出现”动作

#### 编写时的实际痛点

- 当前动作闭集中只有固定起止比例的 `swipe`。面对长列表、设置页底部选项或长度随内容变化的详情页，作者无法预知需要滑动几次，只能堆叠多个 `swipe` + `wait` 步骤，换一台分辨率或字体大小不同的设备就很容易滑过头或滑不到。

#### 改进方向

- 在闭集动作中增加**滚动查找（scroll-to-element / scroll-until）**动作：指定目标定位器、滚动方向（上/下/左/右），可选指定滚动容器定位器与最大滑动次数或时限上限。
- 若滚动到边界或用尽上限仍未出现目标元素，按动作失败返回 `error`；命中后即可紧跟 `tap` 或预期断言。
- 该能力在 Android（`uiautomator2`）和 HarmonyOS NEXT（`uitest`）上均可稳定实现，也容易映射为桌面端原生表单字段。

---

### 3. 断言对元素状态、可见性与数量覆盖不足

#### 编写时的实际痛点

- **常用交互状态无法断言**：`attr_equals` 目前只接受 `enabled` 和 `checked` 两个属性。Android 中极常见的选中态（`selected`，如 Tab 栏、筛选标签）、输入焦点（`focused`）、可点击态（`clickable`）、密码掩码态（`password`）等均无法校验。
- **无法判定元素在屏幕上“真正可见”**：`exists`、`text_equals`、`text_contains` 都直接检查包含屏幕外节点的控件树，即使元素在列表下方未滚出、或被上层浮窗遮挡，断言依然成立；而 `screen_text` 只能识别像素文字，无法检验纯图标或被半遮挡的元素。
- **无法校验列表结果数量**：搜索结果至少有一条、购物车清空后条目数为 0 等场景，只能用 `exists` / `absent` 粗略判断，无法表达“恰好 N 个匹配”或“不少于 N 个匹配”。
- **缺少否定语义的文本断言**：例如确认界面提示中不再包含某错误词时，用 `absent` + 定位器必须保证整元素不存在，无法表达“某元素存在但显示文本不包含某字样”。

#### 改进方向

1. **扩充跨平台标准属性集**：在 `attr_equals` 中评估加入 `selected`、`focused`（Android 底层已解析 `focused` 属性但尚未暴露到 `Element`），以及两端可对齐的 `clickable` / `scrollable` 等状态。
2. **区分“树中存在”与“屏幕内可见”**：增加或扩展可见性断言（如 `visible`），结合屏幕尺寸与节点边界判断是否处于可视区域内。
3. **补充匹配计数断言与否定文本断言**：支持对定位器命中数量做比较（等于/大于/小于），并补充 `text_not_contains` 或 `description_contains`。
4. **继续推进视觉语义断言评估**：针对字体放大裁切文字、纯图形状态变化（如点赞红心）等控件树和屏幕文字都无法表达的场景，按 [`docs/ai-execution.md`](ai-execution.md) 的评估路径完成样本评测后再决定是否引入。

### 4. 输入、按键与启动方式的实用缺口

#### 编写时的实际痛点

- **按键（`key`）过少**：目前仅支持 `back` 和 `home`。在搜索框输入关键词后无法直接按键盘 `enter` / `search` 提交，输入错误后也无法按 `delete` 退格，经常被迫去点输入法右下角的绝对坐标或改用 `ai` 步骤。
- **文本输入（`type`）依赖前提过强且只能整段替换**：
  - 当前实现要求控件树中必须存在 `focused == true` 的节点，并依赖向设备安装/切换 `AdbKeyboard` 执行 `ADB_KEYBOARD_SET_TEXT`。
  - 在安全键盘、未暴露 `focused` 状态的自绘/WebView 输入框、或禁止静默安装 APK（`INSTALL_FAILED_USER_RESTRICTED`）的设备上，输入步骤会直接报错；同时缺少“在光标后追加输入”的能力。
- **`launch` 无法表达冷启动隔离与深链跳转**：
  - 某些测试必须从冷启动状态开始，或通过 DeepLink / 指定 Intent Action 直接拉起目标界面；目前 `launch` 仅调用 `am start -W -n`，应用已在后台时往往只将其切回前台而不会重置界面状态。

#### 改进方向

1. **扩展标准按键集**：在 `key` 中补充两端通用的交互按键，如 `enter`、`search`、`delete`（退格）、`tab`、`recent`（最近任务）等。
2. **增强输入动作的适配模式**：
   - 增加“追加输入”与“替换输入”模式（或提供显式清空动作）；
   - 评估在未暴露 `focused` 节点或无法安装第三方输入法时，是否允许针对纯 ASCII / 已知能力提供回退输入方式，并在报告中保留清晰诊断。
3. **增强应用启动与显式重置动作**：
   - 支持显式停止应用（`stop_app`）或为 `launch` 增加冷启动选项；
   - 支持通过 URI / DeepLink 启动应用界面。

> **与现有设计的一致性说明**：[`docs/design.md`](design.md) 规定“执行开始前不自动清理应用或回到主页，残留界面由前置断言负责”。因此，冷启动或停止应用只能作为作者**显式写进用例的步骤**，不应变成执行器在用例开始前隐式触发的默认行为。

## 二、中优先级：套件规模化与特殊场景缺口

### 1. 公共步骤复用与用例清理段（Teardown）

#### 编写时的实际痛点

- **用例中止后缺少收尾动作**：一旦 `expect` 失败或 `precondition` 阻塞，当前用例立即停下（仅保留 Android 输入法切回）。如果用例中途登录了测试账号、打开了测试开关或新建了草稿数据，后续套件中的下一条用例就会受到残留状态污染。
- **高频前置流程只能复制粘贴**：套件目前只能依次引用完整用例。多条用例共用同一段“登录 → 进入设置页”步骤时，只能复制一份再修改；一旦公共路径改版，需要逐个修改几十个 YAML 文件。

#### 改进方向

- **显式清理段（`teardown` / `finally`）**：允许用例在主步骤之外声明一组清理动作。无论主步骤结果是 `pass`、`fail`、`blocked` 还是 `error`（设备仍在线时），均尽力执行清理段；清理失败仅记入注明或单独标记，不掩盖主步骤已经得出的 `fail` / `blocked` 结论。
- **受限的公共步骤片段引用**：允许用例引用同一仓库内的纯步骤片段文件（无参数或仅带静态常量），由 `Load` 在载入阶段直接静态展开并校验全部路径和字段，使套件、报告步骤序号和桌面端预览仍能保持直观。

---

### 2. 参数化与执行环境数据注入

#### 编写时的实际痛点

- 同一条“登录”或“搜索校验”用例面对不同测试账号、不同环境数据或多种等价类输入时，目前只能把同一份 YAML 复制成多个文件。
- 部分项目不希望把测试账号密码明文提交到用例文件仓库中。

#### 改进方向

- 在不违背“用例不绑定设备和模型”的前提下，评估支持**命名参数占位符**与外部测试数据集（或执行时传入的参数映射），使同一条用例模板可绑定不同输入运行，并在报告中保留实际使用的非敏感参数摘要。

---

### 3. Android 特殊界面与瞬态提示处理

#### 编写时的实际痛点

- **系统 Toast 难以捕获**：Android Toast 存在时间短，且很多版本不会出现在 `dumpWindowHierarchy` 返回的窗口控件树中；当前断言轮询间隔最高为 500ms，极易错过一闪而过的提示（如“密码错误”、“已复制”）。
- **隐私安全界面（`FLAG_SECURE`）强制截图报错**：当前每一步结束后都会强制截图，若截图失败整步即判为 `error`。在登录输密、银行卡/支付确认等开启了 `FLAG_SECURE` 的界面上，用例无法正常继续执行。

#### 改进方向

1. **Toast / 瞬态消息观察能力**：在 Android 设备适配层评估通过 UiAutomation 无障碍事件监听最近一段窗口内的 Toast 文本，供专用断言或提示校验使用。
2. **安全界面截图降级策略**：允许特定步骤声明允许无截图（或当设备明确因受保护界面拒绝截图时，按作者声明的选项记入步骤说明而非直接中止为 `error`），保障支付/登录流可测。

## 三、保留项：不符合当前 Gnosis 设计定位的能力

以下能力在传统 Android UI 自动化框架（如 Appium / Airtest / UiAutomator 测试工程）中较为常见，但与 Gnosis 当前“**跨平台统一闭集步骤、声明式可校验、桌面端表单直接编辑、AI 步骤补齐柔性路径**”的定位存在直接冲突，建议暂不引入或严格限制：

| 候选能力 | 与 Gnosis 当前定位的冲突 | 当前替代方案 | 重新评估的前提条件 |
| --- | --- | --- | --- |
| **条件分支与循环（`if/else`、`while`、脚本表达式）** | 使 YAML 用例滑向编程语言，破坏线性步骤序号、静态可检验性以及桌面端原生表单的简单编辑模型。 | 偶发弹窗或不确定导航路径使用 `ai` 步骤；起始状态校验用 `precondition` 明确暴露阻塞。 | 仅当某类条件模式（如“处理系统权限弹窗”）高频出现到有必要做成受限的声明式开关，而非通用逻辑语法时。 |
| **在用例中直接下发 `adb shell` 或任意设备命令** | 直接违背 [`GLOSSARY.md`](../GLOSSARY.md)（脚本与 AI 只能请求设备操作）和 [ADR-0002](adr/0002-device-protocol-not-cli.md)，也无法映射到 HarmonyOS NEXT。 | 将真正刚需的系统级动作（如停止应用、按键、DeepLink 启动）提炼为封闭、跨平台的设备操作原语。 | 原则上不向普通用例开放；如有极少数调试/环境准备诉求，也应留在执行环境或前置准备钩子中。 |
| **运行时变量捕获与动态计算（读取文本存变量并参与后续拼接/运算）** | 引入运行期状态机和表达式求值，大幅抬高用例理解、报错定位以及 AI 轨迹转草稿（[`docs/roadmap.md`](roadmap.md)）的复杂度。 | 尽量使用固定的测试环境数据保证预期断言确定性；需跨步骤语义判断的场景交给 `ai` 步骤。 | 当已有数据驱动方案后，若发现大量核心业务链路（如“动态生成订单号后去列表核对”）无法通过静态数据构造绕开。 |
| **执行前隐式清理应用、自动回主页或步骤自动重试** | 明确违背 [`docs/design.md`](design.md) 的已定决策；自动清理会掩盖残留界面问题，自动重试会掩盖偶发稳定性缺陷。 | 由 `precondition` 及时阻塞不符的起始状态；需要干净入口时由作者显式写入启动/停止步骤。 | 仅适合作为套件外部的 CI 调度策略，不应内置为单条用例的静默默认行为。 |
| **纯图像切图模板匹配与在线视觉识别** | 模板切图对分辨率、比例和主题切换极其脆弱；在线视觉识别违背 [ADR-0005](adr/0005-onnx-ppocr-in-core.md) 离线执行与截图不出本机的原则。 | 标准界面走控件树，自绘文字走内置离线屏幕文字识别；复杂纯图形判断待后续视觉语义断言方案。 | 仅当本地离线小模型或已授权的视觉语义断言经过误判率验收后再考虑接入 `expect`。 |
| **单进程多设备并发编排与复杂多指轨迹** | 违背 [`docs/design.md`](design.md)（“一台设备同一时间只有一个执行”）与 [`docs/roadmap.md`](roadmap.md) 的单设备边界；多指手势难以在表单和 AI 动作中统一描述。 | 多设备并行由多进程或云端调度（[`docs/execution-control.md`](execution-control.md)）完成。 | 除非产品形态扩展到双端即时交互测试（如通话、IM 实时收发协同），否则保持单设备执行模型。 |

## 四、建议的演进节奏

为避免一次性破坏加载校验和桌面端表单的稳定性，建议按以下顺序小步推进：

1. **第一批（低侵入、收益最高）**：
   - 定位器增加子串匹配（如 `text_contains`）与屏幕内可见过滤；
   - `attr_equals` 补齐 `selected`、`focused`；
   - `key` 补齐 `enter`、`search`、`delete`；
   - 增加显式 `stop_app`（或 `launch` 冷启动/URI 参数）。
2. **第二批（补齐长列表与可维护性）**：
   - 增加“滚动直到定位器出现”动作；
   - 增加容器内相对定位（`within`）与匹配计数断言；
   - 增加用例级显式清理段（`teardown`）和受限的公共步骤片段引用。
3. **第三批（专项边界验证）**：
   - 评估 Android Toast 捕获与 `FLAG_SECURE` 截图降级策略；
   - 结合 AI-assisted case authoring 试点，验证视觉语义断言与轻量参数化方案。
